## 설계 결정 (되돌리지 말 것)

- TS의 1턴 = Godot의 1계절 = 90틱. SimulationCore의 월 예산/계절 재해는 그대로 두고, TurnSystem이 "턴당 추가분"만 더한다.
- 지형은 Tiled 맵이 원천이다. TS의 코너 버텍스 높이맵은 이식하지 않았다(맵이 평면 타일).
- 연구 5종의 비용은 TS에 UI가 없어 Godot에서 임의로 정했다 (CourtSystem.RESEARCH_LIST).
- 건물 그래픽은 PNG 스프라이트가 아니라 CityLayer의 `_draw` 폴리곤이다. 아트 교체 시 `_draw_tile`만 바꾸면 된다.
- `is_connected`는 Godot Object 메서드와 충돌하므로 TradeSystem에서 `trade_connected`로 명명했다.

## 5순위 완료 항목 (P21, P22) — 2026-09-28

사용자가 실제 플레이에서 "도로/성곽이 계속 끊긴다", "국경 교역이 안 된다"고 재보고하여 조사한 결과,
둘 다 렌더링 버그가 아니라 실제 게임 로직 결함이었다.

### P21 — 도로/성곽이 수원천을 못 건너 항상 끊기는 문제 (근본 원인 확정)

`grid.get_road_mask`/시각화 자체는 정상이었다. 실제 원인은 `GameGrid.validate_tool`이 물길(`terrain=="water"`)
위에는 `levee` 외 어떤 것도 못 짓게 막고 있었던 것: 지도를 남북으로 관통하는 수원천이 항상 도로/성곽을
둘로 갈라놓아, 플레이어가 아무리 이어 붙여도 강을 건너는 구간에서 100% 실패한다(디버그: `x=7,8`
물길 타일에 도로 배치 시도 시 매번 "물길 위에는 지을 수 없습니다" 거부, 인접 타일이 끊겨 보임).
→ `GameGrid.BRIDGEABLE = ["road","wall","gate"]`을 물길 금지 예외로 추가하여 다리(목교)/석축 수문으로
강을 건널 수 있게 했다. 오토타일 비트마스크는 그대로 `building=="road"/"wall"/"gate"` 기준이라 다리 타일도
자동으로 이어져 계산된다. 건설 비용은 `GameGrid.get_tool_cost()`로 분리해 수상 구간은 금 3배 + 쌀 15
가산(교각/수문 공사). 렌더링은 `CityLayer._draw_bridge_deck()`이 전용 폴리곤(목교/석축 수문)을 그린다.
(부가로 확인된 사실: 국책 대역사 `suwon_levee`가 시작부터 `is_started=true`라 그 대상 타일 8칸이 항상
공사 중 상태로 건설을 막는다. 이는 의도된 강변 축조 설계이지 버그가 아니므로 그대로 두었다.)

### P22 — 동서남북 4대 교역로 미구현

TS 원본(`checkTradeSystem`)은 애초에 "지도 가장자리에 도로가 한 칸이라도 닿았는가"라는 단일 불리언만
판정했다(1:1 이식은 P4에서 완료). 그러나 참조 설계문서(`docs/simcity2000_reference_architecture.md`)의
"외곽 경계 도달 시 한양/호남/영남/남양만 포구와 연결"이라는 서술을 실제로 구현한 적이 없었고,
효과도 턴 경계(90틱)에만 갱신되어 플레이어 체감상 "아무 반응 없음"으로 보였다.
→ `TradeSystem.gd`를 4방향(북=한양 조운로/금, 남=호남 삼남대로/쌀, 동=영남대로/금, 서=남양만 포구/쌀)
개별 연결 판정으로 재작성. `CityLayer.city_changed` 신호에 `trade.check_routes()`를 직접 연결해
턴을 기다리지 않고 도로를 국경에 붙이는 즉시 연결/개통 토스트가 뜨도록 했다. 관문(성곽 2칸 이내)이
있으면 물자량 2배 + 왕권 소폭 상승, 없으면 밀수로 왕권 소폭 하락(TS 원본 로직 유지, 4방향으로 분산).

## 6순위 완료 항목 (P23) — 2026-09-28: 실제 화성 답사 지도 기반 고정 영토

사용자가 실제 수원 화성 답사 지도/고지도 이미지 6장을 제공하며 "심시티처럼 무작위 지형이 아니라
정해진 영토 위에 도시를 건설"해야 한다고 요청. 기존 지형(사인파 하천 + 원형 산세)은 실제 화성과
무관한 추상 형태였다. `godot_hwashung/generate_map.py`를 전면 재작성했다.

### 설계 근거
답사 지도(이미지1) 기준 화성 성곽 둘레를 20x20 격자에 근사한 폐다각형 `WALL_PATH`(13개 정점,
`generate_map.py` 상단)로 고정했다. 장안문(북)→동북공심돈→동장대→창룡문(동)→동이포루→동남각루
→남수문→팔달문(남)→서남각루→서남암문→서포루(팔달산 서쪽 능선)→화서문(서)→서북공심돈→복귀 순.
점-다각형(ray casting) 판정으로 내부(성 안)/외부(성 밖 미편입지)를 나누고, 팔달산(서쪽, 서장대가
정상), 수원천(북수문~남수문을 잇는 절선), 대유둔전 둔덕(만석거 예정지, 동남쪽 소고지)을 모두
고정 좌표로 배치했다. 매번 다르게 생성되지 않으며, 같은 시드 없이도 항상 동일한 지도가 나온다.

### 실제로 잡은 버그 2가지

1. **타일 렌더링 오프셋 버그(기존 코드, 이번에 발견)** — `TiledMapLoader.gd`가 `tile_idx = gid - 1`로
   한 칸 밀려 읽고 있었다. `generate_map.py`/`generate_tileset.py`의 모든 주석은 "데이터 값 ==
   tiles[] 배열 인덱스"를 직접 가리키도록 쓰여 있었는데(예: "3: 수원천 물"), 로더가 매번 하나
   앞의 타일을 그려 물(3)이 황토 평지(2) 색으로, 모래톱(4)이 물(3) 색으로 보이는 등 지형색이
   전부 밀려 있었다. 오프셋을 제거해 값과 배열 인덱스를 1:1로 맞췄다(`gid=0`은 기존처럼 "타일
   없음"으로 스킵). 이 버그는 P23 이전부터 있었지만 우연히 비슷한 색끼리 섞여 눈에 크게 띄지
   않았다.
2. **성 밖 영토 미차단** — `GameGrid`가 Ground 레이어를 아예 읽지 않아 지도 전체(성 안/밖 구분
   없이)가 건설 가능했다. `terrain == "outside"`를 추가해 성 밖 타일은 철거를 포함해 어떤 도구도
   거부하도록 `validate_tool`에 최우선 검사로 넣었다.

### 그 외 변경
- **봉돈 조건 현실화**: 실제 봉돈은 팔달산이 아니라 성곽 동쪽 능선에 있다. `validate_tool`의
  "봉돈=산악 지형" 요건을 "이미 쌓은 성곽(wall/gate)에 인접"으로 교체하고 `QuestSystem.gd`의
  교지 설명도 수정. (서장대는 실제로도 팔달산 정상이 맞으므로 그대로 유지)
- **성곽 위 관문 허용**: `validate_tool`이 산악 지형에서 `wall`만 허용하고 `gate`는 막고 있던
  누락을 수정(`tool != "wall" and tool != "gate"`).
- **국책 대역사 4종 좌표 전면 갱신**: 수원천 제방(강 양안), 팔달산 서성곽+서장대, 화홍문 북수문+
  장안문 북성곽(관문 좌표가 그대로 북쪽 교역로 관문이 됨), 만석거+대유둔전(동남쪽 둔덕)을 모두
  새 지도의 실좌표로 재배치. 전부 성 안쪽·정확한 지형 조건을 만족하는지 스크립트로 검증.
- **현륭원 재배치**: 기존 (11,14)가 새 지도에서 모래톱과 겹쳐 성 남서쪽 한적한 자리 (6,15)로 이동.
- **교역 시스템(P22)이 4대문 기준으로 재작동**: 성곽이 더 이상 지도 가장자리(x/y=0 또는 size-1)에
  닿지 않으므로, `TradeSystem.GATE_POINTS`(4대문 실좌표, `generate_map.py`의 GATES와 반드시
  동기화)를 기준으로 재판정하도록 교체. 그 자리에 "관문"을 지으면 정식 통관(2배 물자+왕권 상승),
  "도로"만 뚫으면 밀수 취급(왕권 소폭 하락)으로 세분화했다.

### P24 — 지형 입체화 + 맵 10배 확장

**맵 크기**: 20x20 -> 64x64 (면적 약 10.24배, 사용자 요청 "10배는 크게"). `generate_map.py`가
P23의 20그리드 좌표계를 3.2배로 그대로 확대해 성곽 둘레·팔달산·수원천·4대문 비율은 유지했다.

**지형 파이프라인 전면 교체**: 기존에는 Tiled 타일 인덱스(정수)로만 지형을 표현해 고저차를 담을
수 없었다. `generate_map.py`가 (size+1)^2 = 65x65 정점 높이맵을 직접 계산해 `maps/terrain_data.json`
으로 출력한다(가우시안 3x3 스무딩 포함). `hwashung_map.tmj`는 이제 좌표 변환 전용 빈 격자 하나만
담당하며, 지형 시각화는 전부 `CityLayer`가 정점 높이를 읽어 그린다. `GameGrid._build_from_map`이
이 JSON을 읽어 타일별 4개 코너 고도(`corner_elev`)와 평균 고도(`elevation`)를 갖는다.

**렌더링**: `CityLayer.cell_center(x,y,elev)`가 고도만큼 화면을 수직 이동시키고,
`_draw_tile`이 타일의 4개 코너를 각각의 고도로 어긋나게 그려 경사면을 만든다(간이 경사광
셰이딩 포함). 물은 고도가 낮을수록(최저 -2.2) 짙은 남색으로, 산은 높을수록(최고 ~7.5) 암반색으로
보간된다 — "물길도 실제처럼 깊이가 있어야" 요청 반영. 클릭 판정(`world_to_cell`)은 평면 좌표로
1차 추정 후 그 타일의 고도만큼 보정해 재조회하는 1-패스 근사로 고지대/하상에서도 오차를 줄였다.

**성능**: 맵이 4096타일로 커지면서 `distance_to_road`를 타일마다 전체 격자 스캔(`O(size^4)`
전체)하던 방식이 계절 경계마다 심하게 끊길 것이 확실해, `GameGrid.build_road_distance_field()`
(도로 전체를 시작점으로 하는 멀티소스 BFS, O(size^2) 1회)로 교체했다. `CityLayer._draw()`도
카메라가 보는 영역만 역투영해 순회하는 뷰 컬링(`_visible_bounds()`)을 추가해 매 프레임 4096타일
전체를 그리지 않는다.

**부수 발견 버그**: 새 맵으로 바꾸며 "교지 2(도로 5칸)"가 시작하자마자 완료되는 문제를 발견했다.
성문 밖 옛 간선로(아래 P25)가 성 안쪽 몇 칸까지 미리 깔려 있어 플레이어가 아무것도 안 해도
조건을 满족시켰던 것 — `QuestSystem`의 도로 판정을 `GameGrid.count_buildings_inside()`(성 밖
제외)로 바꾸고, `generate_map.py`의 옛 간선로 생성도 실제로 "성 밖"에 진입한 구간만 심도록
고쳤다.

### P25 — 성 밖(城底) 자연발생 취락 + 관공시설 민심 관리

사용자 요청: "성 밖은 도시가 발전함에 따라 스스로 개발되도록", "성문 밖의 길을 중심으로 상업지역이
자연발생하고 민가들도 생겨났던 것", "성 밖의 백성들도 백성으로 취급하고 세금이 징수되고 복지혜택을
받을 수 있어야".

- **옛 간선로 고정 배치**: `generate_map.py`가 4대문에서 성 밖으로 이어지는 짧은 도로를 미리
  깔아둔다(실제로 4대문 밖으로 삼남대로/한양대로가 계속 이어졌던 것의 재현). `GameGrid`가 이
  좌표를 `outbound_roads`로 들고 있다가 초기화 시 `building="road"`로 심는다.
- **자연발생 성장**: `OutsideSettlement.gd`(신규)가 계절 턴마다 이 도로에 인접한 성 밖 빈 평지
  일부에 `res_1`/`com_1`을 스스로 심는다. 성장 속도는 도성 인구·민심에 비례하고, 관공시설
  (동헌/순라청/멸화군, 기존 `GameGrid.has_security_coverage` 재사용) 치안망이 없는 곳은 절반
  확률로 정착이 무산된다(도적/화재 등으로 실패하는 느낌).
  - **별도 세제를 만들지 않음**: 심어진 `res_1`/`com_1`은 성 안 건물과 똑같은 타입이므로
    `GameGrid.develop_and_harvest`(인구·세수 집계, res_1->res_2 승급)와 `SimulationCore`의
    기존 조세/구휼 로직을 그대로 탄다. 즉 "성 밖 백성도 백성으로 취급"이 별도 코드 없이
    코드 구조상 보장된다.
- **관공시설로 민심 관리**: `GameGrid.validate_tool`이 성 밖에서는 `road`/`well`/`office`/
  `patrol`/`firefighter`만 허용하도록 바꿨다(구획·성곽 등 정식 도성 시설은 여전히 성 안 전용).
  `OutsideSettlement.unrest_delta()`가 치안 공백이 절반 넘으면 민심 하락, 완전 관리되면 소폭
  상승을 매 턴 반영한다. 순라청/멸화군은 아직 건물 아틀라스 스프라이트가 없어 `CityLayer`에
  임시 깃발 마커로 표시했다(추후 아틀라스에 슬롯 추가 시 `BUILDING_SLOTS`로 옮길 것).
- **UI**: 툴바에 "성저(城底) 민정" 버튼을 추가해 민가/저잣거리 수, 추정 인구, 치안망 커버리지를
  볼 수 있다.

사용자가 외부 문서(`2000.md`, 《화성신시 1794》 청사진)를 기준으로 "심시티 2000급 초경량 구동"

전답·저잣거리 자연 승급에 수원·치안 조건 추가, 관공시설(순라청/멸화군/공심돈/포루/연무대/
방화수류정/용연) 다수 신규, UI 전면 개편)를 검토하고, 그 과정에서 어긋난 계약 3건과 경량화
위반 1건을 발견해 고쳤다. 전체 파일을 덮어쓰지 않고 부분 `Edit`로만 반영했다.

### 발견 및 수정한 실제 버그 (동시 편집 중 발생한 계약 불일치)

1. **`turn_report` 시그널 인자 불일치 (매 턴 런타임 에러)** — `TurnSystem`은
   `(article: Dictionary, dilemma: bool)` 2개 인자를 계속 내보내고 있었는데, `PanelController`는
   `_on_turn_report(rep: Dictionary)` 인자 1개짜리로 리팩터되어 있어 **매 계절 경계마다**
   `Method expected 1 argument(s), but called with 2` 에러가 발생하고 있었다. 그 여파로
   3턴마다 뜨던 암행어사 딜레마 팝업(`NewspaperSystem.dilemma_pool`)이 완전히 죽어 있었다.
   → `turn_report(rep: Dictionary)` 단일 계약으로 통일하고, `PanelController`에 딜레마 트리거를
   되살렸다(`_show_dilemma()`).
2. **`outside.settlements` 미정의 참조** — 새 "성저 민정" 패널이 `outside.settlements.size()`를
   읽는데 `OutsideSettlement`엔 그런 프로퍼티가 없어 패널을 열면 즉시 오류가 났다. `grow()`가
   심을 때마다 좌표를 기록하는 `settlements: Array[Vector2i]`를 추가했다.
3. **맵 확장(P24, 64x64) 후 갱신되지 않은 카메라 중심** — `CameraController.reset_view()`와
   `Main._ready()`의 초기 카메라 위치가 옛 20그리드 중심 `(0,320)`에 고정되어 있어, "화면 중앙"
   버튼과 최초 진입 화면이 실제 지도 북서쪽 구석을 비추고 있었다. `(0,1024)`(64그리드 중심)로 수정.
4. **테스트 하네스 API 드리프트** — `CityLayer`가 드래그/Undo 시스템으로 바뀌며 단일 타일
   헬퍼 `_apply_at()`가 삭제되고 `_apply_batch_build(tiles, tool)`로 대체되어 `smoke_test.gd`가
   전부 깨져 있었다. 테스트를 새 API로 갱신.

### 경량화 위반 및 조치

- **`CitizenManager._process(delta)`가 매 프레임(60FPS) 64x64=4096타일 전체를 훑어 도로 목록을
  새로 만들고 있었다** — 청사진이 명시적으로 금지한 "렌더링 루프 안에서 무거운 타일 순회 루프
  실행"의 정석적인 사례. `grid.grid_changed` 시그널이 올 때(건설/철거 시)만 캐시를 갱신하도록
  고쳤다(`_roads_cache`/`_roads_dirty`). 유휴 상태에서는 매 프레임 0회 순회.
- **`GameGrid.apply_tool()`이 호출마다 `recompute_infrastructure()`(4096타일 전체 스캔)를
  돌리고 있었다** — 드래그 한 번으로 성곽/도로 수십~수백 칸을 잇는 `_apply_batch_build`가 타일당
  1회씩 이 함수를 부르므로, 긴 성곽을 한 번 그으면 마우스를 뗄 때까지 전체 격자 스캔이 N번
  반복되어 눈에 띄는 끊김이 났다. 호출부가 배치 종료 후 이미 자체적으로
  `recompute_infrastructure()`/`update_fortress()`를 부르므로 내부 자동 호출을 제거했다
  (드래그 1회당 스캔 횟수가 N+2 → 2로 감소).
- 죽은 코드 정리: `get_wall_mask`의 `if is_road_connector(...): pass` no-op 줄 제거.

### 감사 결과 — 이미 잘 지켜지고 있던 것 (건드리지 않음)

- `PointLight2D`/`DirectionalLight2D`/포스트프로세싱 셰이더/물리 바디(`CharacterBody2D`,
  `RigidBody2D`)/`NavigationServer2D`/GPU 파티클: 코드베이스 전체 검색 결과 **전무**. 이미 순수
  `_draw()` 즉시 모드 폴리곤 렌더러 + 풀링된 시민 딕셔너리 배열 구조라 청사진의 하드 제약을
  원래부터 위반하지 않고 있었다.
- 건축 단계 연출: 국책 대역사 공사 중 비계/거중기 스프라이트(`under_construction`)가 이미 있다.
- 앰비언트 행인: `CitizenManager`가 지게꾼/보부상/장용영/농민을 오브젝트 풀(최대 수십)로 도로를
  따라 배회시키고 있다(개별 길찾기 없음).
- 시뮬레이션/렌더 분리: `TimeManager`가 프레임과 무관한 축적식 틱을, 무거운 격자 연산
  (`develop_and_harvest`, RCI 성장, 조세)은 계절 경계(틱 90개=1계절)에만 실행한다.

### 남은 것 (이번 범위에서 건드리지 않음)

## 9순위: 체감 프레임 저하 대응 + 인게임 지형 편집기 (P27) — 2026-09-28

사용자가 "뚝뚝 끊긴다"는 체감 저하와, 자동 생성 지형(팔달산 정상 위치, 행궁 자리, 수원천 경로가
실제 답사 지도와 다름)을 직접 고치고 싶다는 요청을 함께 제기.

### 성능: 월드 재도색 30Hz로 스로틀링

`CityLayer._process`가 매 프레임(60Hz) `queue_redraw()`를 불러 전체 가시 영역을 다시 그리고
있었다. 도로/성곽/홍예문 한 타일이 연결부 폴리곤·선·원 등 수십 개의 개별 `draw_*` 호출로
그려지는 구조라(64x64 확장 이후 화면을 채우는 타일 수도 많아짐), 도시가 어느 정도 차면
프레임당 그리기 명령 총량이 상당해진다. 애니메이션 시계(`_anim`)는 계속 60Hz로 갱신하되
실제 `queue_redraw()`는 30Hz로 낮춰 프레임당 그리기 명령 총량을 절반으로 줄였다. 건설/철거
(`grid_changed`)·화면 회전·드래그 중 마우스 이동은 별도로 즉시 `queue_redraw()`를 부르므로
조작 반응성은 그대로 즉각적이다.

**참고**: 이번에 찾지 못한 것 — 사용자가 캡처한 스크린샷에 있던 부드러운 회색 흐림 얼룩은
코드베이스 전체를 검색해도 파티클/조명/날씨/블러 관련 코드가 전혀 없어 원인을 특정하지
못했다. 스크린샷 상단 툴바(입력/2D/3D 토글)로 보아 Godot **에디터의 2D 뷰포트**를 찍은
것으로 보이므로, 에디터 자체의 선택 하이라이트이거나 WEBP 압축 아티팩트일 가능성이 높다.
실제 실행(컴파일/플레이) 화면에서도 나타나는지 확인이 필요하다.

**근본적 해법(보류)**: 청사진이 요구하는 "심시티 2000급" 성능을 확실히 담보하려면, 정적
타일(도로·성곽·건물)을 매 프레임 다시 그리지 않고 텍스처(SubViewport 캐시 또는 실제
TileMapLayer)로 한 번 굽고, 그 위에 움직이는 시민만 매 프레임 다시 그리는 구조가 정석이다.
`CityLayer.gd`가 계속 활발히 바뀌고 있어 이번에는 30Hz 스로틀링까지만 하고, 렌더 아키텍처
전면 교체는 보류했다.

### 인게임 지형 편집기 (신규)

`GameGrid`에 공유 정점 높이맵(`vertex_heights`, (size+1)x(size+1))을 런타임에 유지하도록
바꿨다(기존엔 타일마다 한 번 계산해 캐시만 남기고 원본을 버렸음). `paint_terrain(cx, cy, kind,
radius)`가 붓 반경 내 타일의 지형 종류와 정점 높이를 다시 쓰고, 그 정점을 공유하는 이웃 타일
(붓 경계 바깥 1칸 포함)까지 다시 계산해 이음매 없이 이어지게 한다.

- **새 도구 3종**: 평지 붓(`terra_plain`)/산 붓(`terra_mountain`)/물 붓(`terra_water`).
  하단 도크바에 "🗺️ 지형편집" 버튼(관청·공공 옆)을 누르면 서브 도크로 뜬다.
- 건설 도구(비용·검증·Undo)를 전혀 거치지 않는 **지도 설계 전용** 도구다. 성 안/밖 구분 없이
  어디든 무료로 칠할 수 있다 — 국책사업이나 4대문 같은 게임 밸런스 요소가 아니라 "지형 그 자체"를
  고치는 것이므로.
- 드래그하면 브레젠험 직선으로 죽 이어 그려진다(도로/성곽 드래그와 동일한 조작감).
- 검증: (30,30)에 산을 그리자 이웃 타일과 공유 변 높이가 정확히 일치(이음매 없음)했고,
  원래 서장대 정상 자리(13,29)를 평지 붓으로 깎아낸 뒤 그 자리에 동헌을 지을 수 있음을 확인.
  스크린샷으로 팔달산을 통째로 밀어 평지로 만들고 강 건너 반대편에 새 봉우리(+서장대)를
  세우는 시나리오까지 실제로 렌더링 확인.

### 검증
```
Godot_console.exe --headless --path godot_hwashung --import
Godot_console.exe --headless --path godot_hwashung -s res://tests/smoke_test.gd
```
기존 6대 교지·8대 엔딩·거중기 가속 전부 회귀 없이 통과. 지형 붓 이음매·팔레트 교체 시나리오는
임시 스크립트로 확인 후 삭제.

### 다음에 참고할 것
- 지도를 다시 `generate_map.py`로 재생성하면 플레이어가 붓으로 고친 내용은 사라진다(그건
  원본 데이터일 뿐이다). 플레이어가 그린 지형을 저장하고 싶다면 `GameGrid.vertex_heights`+
  `terrain` 배열을 별도 세이브 파일로 직렬화하는 기능이 필요한데, 이번 범위에는 없다(세이브/로드
  시스템 자체가 아직 없음).
- `paint_terrain`은 지형 위에 있던 건물/구획을 그 자리에서 지운다(산 위에 있던 건물이 사라지는
  식). 국책 대역사 대상 타일이나 4대문 위치를 붓으로 밀어버리면 그 지점의 특수 좌표 의미
  (예: `TradeSystem.GATE_POINTS`)는 코드상 그대로 남아있지만 실제 지형은 바뀌므로, 극단적으로
  사용하면 자기 모순적인 지도가 될 수 있다(예: 성문 좌표가 물 밑에 잠기는 등). 필요하면 4대문/
  국책사업 좌표 반경은 붓질 금지 구역으로 보호하는 것을 다음 개선으로 고려.

## 10순위: 텍스처 베이크 렌더러 + 지형 손수 제작·저장 (P28) — 2026-09-28

### 텍스처 베이크: "구워두고 시민만 매 프레임 그리기"

`CityLayer`를 두 인스턴스로 분리했다.
- **`city`** (기존 인스턴스, `Main` 트리에 그대로 존재): 입력 처리·드래그 건설·Undo·지형
  편집 로직을 전부 그대로 담당하지만 `visible = false`로 꺼둬서 화면에는 아무것도 안 그린다
  (Godot는 보이지 않는 CanvasItem의 `_draw()`를 애초에 호출하지 않으므로 그리기 비용이 0이다).
- **`baker`** (신규 `CityLayer` 인스턴스, `SubViewport` 자식): 시민 없이(citizens=null) 지도
  전체를 그린다. `grid_changed`/`rotate_view`가 일어날 때만 `queue_redraw()`가 호출되고,
  그 결과가 `SubViewport` 텍스처로 구워진다. 뷰 컬링을 없애고 매번 지도 전체를 그리는데,
  어차피 드물게만 호출되므로 카메라를 어디로 움직여도(패닝/줌) 다시 그릴 필요가 없다.
- **`world_sprite`** (`Sprite2D`, `Main` 트리): `baker`가 구운 텍스처를 실제 화면(카메라
  영향권)에 표시한다. `TEXTURE_FILTER_NEAREST`로 픽셀아트가 흐려지지 않게 했다.
- **`CitizenLayer.gd`** (신규): 실제로 "움직이는" 것—시민 에이전트, 마우스 호버 커서, 드래그
  건설 미리보기—만 60fps로 매 프레임 그린다. `CityLayer`의 좌표 변환 함수(`cell_center`,
  `_rotate_pos` 등, 순수 계산이라 안전하게 재사용 가능)를 참조해 정확히 같은 위치에 그린다.

`Main._compute_world_bounds()`가 지도 4모서리를 최저/최고 고도(지형 붓의 산/물 범위 포함)로
투영해 SubViewport 크기·위치를 계산하고, `_rebake_world()`가 건설/철거/지형편집/회전마다
호출되어 다시 굽는다. 검증: 건설 후 스크린샷으로 구운 결과(동헌·관문·도로) 확인, 회전 후
재굽기도 정상 확인. 기존 6대 교지·8대 엔딩 회귀 없음.

**트레이드오프**: 정적 레이어(봉돈 연기 등)의 애니메이션은 이제 "다음에 다시 구워질 때"만
갱신된다(요청 그대로 — "움직이는 시민만 매 프레임"). 유휴 상태에서는 완전히 멈춰 보인다.

### 지형 손수 제작 + 영구 저장

기존 인게임 지형 붓(P27, 평지/산/물)에 **"💾 지형 저장"** 버튼을 추가했다
(`GameGrid.export_terrain_data()`). 개발자가 실제 화성 참고 지도를 보며 붓으로 산 정상·
행궁 자리·하천을 원하는 대로 그린 뒤 이 버튼을 누르면 `maps/terrain_data.json`을 덮어써
**모든 플레이어의 새 기본 지형**이 된다(플레이어가 매번 다시 그릴 필요 없음). 기존 파일은
`terrain_data.backup.json`으로 한 번 백업한 뒤 덮어쓴다. 검증: (5,5)에 산을 그리고 저장 →
새 `GameGrid` 인스턴스로 재로드 → 저장된 지형이 그대로 불러와지는 것을 확인.

### 검증
```
Godot_console.exe --headless --path godot_hwashung --import
Godot_console.exe --headless --path godot_hwashung -s res://tests/smoke_test.gd
```
저장/재로드 시나리오는 실제 `maps/terrain_data.json`을 건드리므로, 테스트 전 파일을 백업하고
테스트 후 원본으로 복원했다(백업 파일은 정리해 남기지 않음).

### 참고: 이번에도 겪은 동시 편집 충돌
`GameGrid.gd`에 `export_terrain_data()`를 처음 삽입한 직후 파일이 다시 확인해보니 해당 함수가
통째로 사라져 있었다(다른 세션의 동시 저장과 충돌한 것으로 추정). 재삽입 후 즉시 재검증하는
방식으로 대응했다. 이 프로젝트가 세션 밖에서도 활발히 편집되고 있다는 점을 계속 감안할 것.

### 다음에 참고할 것
- SubViewport 텍스처 크기가 지도 크기에 비례한다(64x64 기준 약 4536x2632, ~48MB). 맵을 더
  키우면 일부 구형/저사양 GPU의 최대 텍스처 크기(보통 4096~16384)를 넘을 수 있으니 확인 필요.
- `city`(입력 담당)와 `baker`(렌더 담당) 두 인스턴스가 같은 `grid`/`ref_layer`를 공유한다.
  둘 중 하나만 고치고 다른 쪽을 안 고치는 식의 향후 수정 시 혼선에 주의(예: `rotation_step`은
  `_rebake_world()`가 매번 `baker.rotation_step = city.rotation_step`으로 동기화해준다).
- `export_terrain_data()`는 지금 UI 어디서나(플레이어 화면에서도) 누를 수 있다. 개발자 전용
  기능이라면 추후 디버그 모드 플래그로 감출 수 있다.

## 11순위: 산 블록 쌓기 + 산길·산성 연결 (P29) — 2026-09-28

사용자 요청: "산의 높이를 블록 쌓듯이 높일 수 있으면 좋겠다", "산에도 산성을 연결하고 길을
연결할 수 있어야 해. 실제로 성은 산길을 타고 만들어졌고 산 속에 길도 있었어."

### 산 붓 -> 블록 쌓기 방식으로 변경

기존엔 산 붓을 칠하면 항상 고정 높이(5.0)로 덮어썼다. 이제는 `GameGrid._paint_mountain_block()`
이 클릭(드래그 1획)마다 붓 반경의 공유 정점 높이를 정확히 **+1.0**씩만 누적으로 올린다
(`MOUNTAIN_BLOCK_STEP`, 상한 `MOUNTAIN_MAX_HEIGHT=10.0`). 같은 자리를 여러 번 클릭하면
계단식으로 점점 높아져 "블록을 쌓는" 느낌을 낸다. 평지/물 붓은 기존처럼 고정 높이 그대로다
(행궁 자리를 깎아 평평하게 만드는 용도라 절대값 설정이 맞다).

### 산길(도로)과 산성(성곽) 연결

`GameGrid.validate_tool`이 산악 지형에서 성곽·관문만 허용하고 도로는 막고 있었다. 실제
화성은 팔달산 능선을 따라 성곽이 이어지고 그 안쪽에 순찰로가 있었으므로, 도로도 산악
지형에 낼 수 있게 허용했다(`tool != "road"` 예외 추가). 산을 쌓을 때 이미 있는 도로/성곽/
관문은 밀어버리지 않고 높이만 올린다(`_paint_mountain_block`이 `road`/`wall`/`gate`는
건물을 지우지 않고 지형만 mountain으로 바꾼다) — 산성이 산과 함께 솟아오르는 모양이 된다.

검증: (10,10)에 6번 연속 클릭 -> 고도가 1.0씩 정확히 누적(2.0→7.0), 15회 추가 클릭해도
상한 10.0을 넘지 않음. 산 위에 도로/성곽 배치 허용, 동헌 등 일반 시설은 여전히 차단 확인.
스크린샷으로 새로 쌓은 봉우리 위로 산길이 넘어가고 능선을 따라 성곽이 서는 것, 도로와
성곽이 만나는 정상에서 자동으로 홍예성문(관문)으로 승격되는 것까지 확인했다.

### 관찰(추가 조사 필요, 이번엔 미해결)
검증 스크린샷에서 성곽 안쪽 수원천 가장자리에 부드러운 흐림 얼룩이 다시 나타났다. 이번
텍스처 베이크(P28) 파이프라인과 관련이 있을 가능성이 높다 — SubViewport로 구운 텍스처를
Sprite2D로 표시할 때 `TEXTURE_FILTER_NEAREST`를 쓰고 있는데, 카메라 줌이 1:1 정수배가 아니면
(예: 1.1배) 물가의 그라데이션(버텍스 컬러 보간, `_calc_vertex_color`) 부분에서 최근접 샘플링과
비정수 확대율이 겹쳐 얼룩덜룩하게 뭉개져 보일 수 있다. 사용자가 최초 보고했던 흐림 현상과
같은 원인일 가능성이 있다. 다음 조사 시: 카메라 줌을 텍스처 원본 배율(1.0)에 가깝게 스냅
하거나, 물 표면처럼 그라데이션이 큰 영역만 `LINEAR` 필터로 개별 처리하는 방안을 검토할 것.

## 12순위: 도로/성곽 대각선 연결 + 화성행궁 건물 추가 (P30) — 2026-09-28

### 대각선 연결

사용자 요청: "길이 십자로 연결되는 건 잘 연결되는데 대각선으로 되어 있는 길은 끊겨 보인다."
`get_road_mask`/`get_wall_mask`가 직교 4방향(N/E/S/W)만 검사해서, 계단식으로 대각선으로

- `GameGrid.get_road_diag_mask`/`get_wall_diag_mask` 신규: 대각 이웃(NE/SE/SW/NW)이 연결체이고,
  그 사이 두 직교 이웃이 "둘 다는" 연결체가 아닐 때만 대각선 비트를 켠다(이미 ㄱ자로 직교

  `_draw_wall_diag()`(성곽, 옆면 2장 + 보도 상판 + 여장 두겁석)가 이 공유 꼭짓점까지 이어
  그려서, 이웃 타일이 그리는 반대쪽 스텁과 정확히 같은 점에서 만난다.
- 첫 구현은 스텁 폭이 너무 얇아(도로 rw*0.55, 성곽 perp 5px) 고립 표시용 굵은 원/탑과 비교해

  보도 상판을 추가해 정통 직교 성곽과 비슷한 두께로 맞췄다.
- 검증: (15,30)~(22,37) 8칸 계단식 도로/성곽을 각각 놓고 중간 타일의 대각 마스크가 예상대로
  나오는지(NW+SE=10) 확인, 스크린샷으로 처음엔 점선처럼 보이던 것이 폭 조정 후 실선처럼

## 14순위: 화성행궁 5x5 전용 레이아웃 재설계 + 4대문(장안문/팔달문/화서문/창룡문) 개별 구현 (P32)

작성 시각: 2026-09-28

### 배경
사용자가 실제 화성행궁 항공사진(신풍루 정문-내정-봉수당 정궁-좌우 행각 회랑 배치)과
장안문·팔달문·화서문·창룡문 각각의 실제 사진을 보내며, "행궁을 5x5 전용 레이아웃으로",
"문마다 독특한 구조(옹성 모양·문루 층수)를 살려서" 구현해 달라고 요청했다.

### 1. 행궁 5x5 재설계 — 앵커 픽셀 오프셋 방식 폐기, 타일별 부재 분산 방식으로 교체
- 최초 구현은 `SITE_BUILDINGS["haenggung"]`의 앵커 타일 `c` 하나에서 픽셀 오프셋만으로 정문
  (+70,+…)/연못(-118,+…)/후원(±58,-64) 등 5x5 전체를 그렸다. 그런데 `CityLayer._draw()`가
  타일을 화면 깊이(x+y, `_rotate_pos` 이후) 순으로 정렬해 그리는 페인터스 알고리즘이라, 앵커
  밖으로 멀리 번져 그린 부분이 나중에 그려지는 이웃 타일의 바닥 폴리곤에 뒤덮여 스크린샷에서
  보이지 않는 문제가 있었다.
- 해법: `GameGrid.gd`의 `HAENGGUNG_LAYOUT`(앵커 기준 상대좌표 Vector2i -> 부재 이름 딕셔너리,
  `CityLayer.gd`에 정의)로 5x5(radius=2) 각 칸이 정문/정궁/별당/annex/wing/corridor/연못 중
  자기 몫만 자기 타일 좌표계(c, p_n/p_e/p_s/p_w)에서 그리게 나눴다. `_draw_tile`에서
  `b == "haenggung"`(앵커, rel=0,0)과 `b == "haenggung_site"`(확장 타일, rel = 좌표-site_anchor)
  둘 다 `_draw_haenggung_part(rel, ...)`로 분기한다. 이러면 항상 자기 타일의 정상적인 페인터스
  깊이 순서를 따르므로 이웃에 가려지지 않는다.
- `SITE_BUILDINGS["haenggung"]`도 `radius:1→2, turns:4→6, cost_per_turn` 상향(3x3→5x5).
- 회랑(행각) 조각은 `_draw_haenggung_corridor(p1,p2)`가 타일 자신의 꼭짓점만 이어 그리므로
  옆 회랑 조각과 자연히 이어져 보인다(도로/성곽 대각선 커넥터와 같은 원리).

### 2. 4대문 개별 구현 — 공통 반원/원형 옹성 헬퍼 + 공통 문루 헬퍼
- `_draw_ongseong(c, dir0, r_out, r_in, sweep_deg, squash, wall_col, dark_col) -> Vector2`:
  성문이 바라보는 방향(dir0, 기존 아치 위치 계산과 같은 축)을 기준으로 부채꼴 옹성을 그린다.
  절대각이 아니라 방향 벡터 기준이라 4방향 화면 회전(`rotate_view`)에서도 항상 올바른 쪽을
  향한다. 반환값은 홍예 아치를 그릴 중심점.
- `_draw_gate_pavilion(pc, tiers, scale, gate_name)`: tiers=1(화서문·창룡문, 실제로 단층 문루)
  / tiers=2(장안문·팔달문, 중층). scale로 웅장함 조절(장안문이 가장 큼).
- 문 이름(gate_name) 접두어로 분기: "장안문"→`_draw_janganmun`(반원 대옹성+최대 2층+오색기),
  "팔달문"→`_draw_paldalmun`(거의 완전한 원형에 가까운 큰 옹성+2층), "화서문"→`_draw_hwaseomun`
  (작은 반원형 옹성+단층), "창룡문"→`_draw_changnyongmun`(화서문과 같은 개방형 반원 계열이나
  더 넓게 감싸고 옹성 위에 깃발). 이름이 없거나 다른 문(예: 성저 암문)은 기존 범용 `_draw_gate`
  본체(2층, 옹성 없음)를 그대로 쓴다.

### 렌더링 버그와 수정 — `draw_colored_polygon`이 오목한 반지형 폴리곤을 못 채움
- 처음엔 옹성을 outer 호(24구간, 바깥 반지름) + inner 호(역순, 안 반지름)를 이어붙인 50점짜리
  오목(concave) 폴리곤 하나로 만들어 `draw_colored_polygon`에 통째로 넘겼다. 실행해보면 테두리
  선(`draw_line`)과 성가퀴(`draw_rect`)는 정상 출력되는데 **채우기(fill)만 완전히 비어 보였다**
  — Godot의 폴리곤 삼각분할이 이런 오목한 반지 모양에서 실패하는 것으로 보인다(원인을 좁히려고
  디버그용 밝은 색·점 마커를 넣어 스크린샷으로 직접 확인).
- 수정: 매 구간(outer[i],outer[i+1],inner[i+1],inner[i])을 4점짜리 볼록(convex) 사다리꼴로
  쪼개 `for i in range(seg): draw_colored_polygon(quad, wall_col)`로 각각 채운다. 볼록 사각형은
  삼각분할이 항상 안전하다.
- 2차 문제: `oc`(옹성 중심)를 `c + dir0*(r_out*0.12)`로 거의 안 띄워서, 옹성이 육축(기단) 밖으로
  거의 안 나와 아치 옆에 작은 장식처럼만 보였다(실제 사진처럼 성문 전체를 넉넉히 감싸지 못함).
  `0.12 → 0.55`로 올려 dir0 방향으로 확실히 밀어내자 실제 사진처럼 성문 앞으로 둥글게 튀어나온
  옹성이 보이게 되었다.

### 3. 되돌리기(Undo) 지연 버그 수정
- `CityLayer.undo()`가 grid 데이터는 즉시 고치지만 `GameGrid.grid_changed` 신호를 직접
  내보내지 않았다. 이 게임은 텍스처 베이크 구조(SubViewport)라 `grid_changed`가 와야만
  화면(`world_sprite`)이 다시 구워지는데, undo는 그 신호를 안 보내서 다음 턴 경계(체감상
  수십 초 뒤)에야 우연히 다시 구워져 "되돌렸는데 한참 있다가 사라진다"처럼 보였다.
  `undo()` 끝에 `grid.emit_signal("grid_changed")`를 추가해 다른 건설/철거처럼 즉시 반영.

### 4. 지형 붓 세분화 — 물 깊이 3단계, 산 깎기 추가
- 기존엔 "물 붓"이 무조건 고정된 깊은 물(-1.5)만, "산"은 오직 쌓기(+1블록)만 가능해서
  "산을 깎으면(=평지 붓으로 덮어써서) 가파른 절벽이 생긴다"는 문제가 있었다.
- `TERRAIN_PAINT_HEIGHT`에 `water_shallow`(0.5, 걸어서 건널 여울)/`water`(-0.4, 보통)/
  `water_deep`(-1.5, 기존 깊은 물)를 추가. terrain 필드는 셋 다 "water"로 저장해 교량 등
  기존 로직과 호환.
- `_paint_mountain_block(cx,cy,radius,step)`이 부호 있는 step을 받도록 일반화 —
  `terra_mountain_down` 도구가 `-MOUNTAIN_BLOCK_STEP`을 넘겨 산 쌓기와 같은 1블록 단위로
  거꾸로 깎는다. 네 꼭짓점이 모두 평지 높이까지 내려오면 terrain을 "plain"으로 되돌려
  건설 규칙(`t["terrain"]=="mountain"` 판정)이 시각적 높이와 어긋나지 않게 했다.
- `PanelController`의 지형편집 서브 도크에 "산 깎기"/"얕은 여울"/"물 붓(보통)"/"깊은 물"

- 근본 수정: 모서리 "중점"이 아니라 실제 타일 모서리 전체(`p_n↔p_e`, `p_e↔p_s`, `p_s↔p_w`,
  `p_w↔p_n` — 이웃 타일과 정확히 맞물리는 꼭짓점)를 옆면으로 그린다. 이러면 이웃 타일과
  틈 없이 완전히 이어진다. 상판(성도)도 타일 중앙의 작은 다이아몬드 대신 `[t_n,t_e,t_s,t_w]`
  전체를 채워 이웃 상판과 이어지게 했다.
- 여장(성가퀴)은 `_draw_wall_merlons(t1,t2,col)` 함수로 분리해 각 연결 모서리마다 규칙적인
  총안 이빨을 배치.
- 대각선 커넥터(`_draw_wall_diag`)도 두께를 7 -> 16으로 키워 정방향 옆면과 이음매에서
  갑자기 얇아지지 않게 맞췄다.
- 색 구성도 정리: 남·동쪽(카메라 정면, `we`/`ws`)은 밝은 화강암(`col_stone`), 북·서쪽
  (카메라 후면, `wn`/`ww`)은 어두운 음영(`col_shade`)으로 통일(기존엔 방향별로 석재/전돌
  2단 텍스처가 섞여 있어 색이 뒤죽박죽이었다).

## 19순위: 성곽 모서리 보강 (코너 타워), 모듈형 부재 카탈로그 참고 (P36)

작성 시각: 2026-09-29

사용자가 화성 성곽 모듈형 부재 카탈로그(구역·성벽·성문·망루·조경 5개 분류, 각 부재의 칸수
표기)와 "CONTINUOUS FORTRESS WALL" 개념도(연결점에서도 상판이 끊기지 않는 매끈한 성벽)를
보내며 "이걸 활용해 성벽 이미지를 완성하라"고 요청. 함께 첨부된 인게임 스크린샷은 P35 이전
(중점 띠 방식 시절)의 "이빨 모양 기둥 + 틈" 패턴과 픽셀 단위로 동일해 보여, P35에서 이미 고친
빌드가 아직 반영 안 된 상태(재-import 전 또는 이전 스크린샷 재사용)로 보인다 — 사용자에게
다시 불러와서 확인해 달라고 안내했다(직접 재검증 테스트는 사용자 지시대로 실행하지 않았다).

카탈로그의 "WALL ANGLE (CORNER TOWER)" 개념을 참고해 실제 개선도 추가했다: 직각으로 꺾이는
지점(예: 북쪽+동쪽 이웃만 있고 남·서쪽은 없는 경우)은 두 옆면이 단순히 만나기만 하는 대신,
`_draw_wall_corner_post(corner_pt, wh, col, battle_col)`로 공유 꼭짓점에 벽보다 8px 더 높은
사각 기둥 + 총안 캡을 세워 참고 이미지처럼 모서리가 보강된 웅장한 느낌을 낸다.

### 검증

실행하지 않음 — "테스트는 내가 시킬 때만 해라"). 사용자가 직접 인게임에서 확인 예정.

### 후속: 코너 타워가 만든 회귀 버그 — 되돌림
사용자가 산비탈을 타고 올라가는 성곽에서 비정상적으로 길쭉한 세로 기둥(탑처럼 100px 이상)이
생긴 스크린샷을 보내왔다. 원인은 바로 위 코너 타워 추가 — `_draw_wall_corner_post`가 "직각
이웃 2방향(꺾이는 지점)"마다 호출되는데, 이 게임의 성곽은 대각선 경로를 실제 대각 연결이
아니라 "한 칸씩 번갈아 꺾는 계단식"(예: 북→동→북→동…)으로 쌓는 경우가 흔하다 — 그런 계단식
구간은 매 칸이 전부 "꺾이는 지점"이라 매 칸마다 기둥이 하나씩 생기고, 경사를 타고 올라가며
그 기둥들이 화면상 수직으로 겹쳐 찍혀 마치 하나의 거대한 탑처럼 보였다.
→ `_draw_wall_corner_post` 호출과 함수 자체를 완전히 제거했다(코너 보강 아이디어 자체를
폐기 — 계단식 성곽이 이 게임에서 매우 흔해서 안전하게 넣을 방법이 마땅치 않다). 순수 코너
보강 없이 P35의 전체 모서리 채우기 방식만 유지.

### 검증

## 20순위: 성곽 렌더링 모델 전면 교체 — 허브 + 팔(arm) 방식 (P37)

작성 시각: 2026-09-29

사용자 스크린샷: 성곽이 `--------` 처럼 이어지지 않고 `| | | | |` 처럼 진행 방향에 수직인
평행 판자들로 그려짐.

### 원인 (P35 방식의 근본 오류)
P35는 "이웃과 연결된 모서리"(wn이면 p_n↔p_e 등)에 옆면을 세웠다. 그런데 이웃과 맞닿는
모서리는 성벽이 **지나가는** 내부 경계다. 거기 세운 면은 진행 방향에 수직인 칸막이가 되므로,
한 줄로 이어진 성벽이 칸막이 판자의 나열로 보였다. (P34 이전의 "좁은 띠" 방식도 같은 위치에
면을 세웠던 것이라 같은 계열의 문제였다.)

### 새 모델
- 각 성곽 타일 = 중앙 **허브**(작은 사각 상자) + 연결된 이웃 방향마다 **팔**(상자) 하나.
- 팔은 허브 가장자리 s에서 공유 모서리 중점 m까지 뻗고, 두께 벡터 w는 그 모서리 방향
  `(b - a) * WALL_THICK_K`. 이웃 타일도 같은 모서리(같은 두 꼭짓점)에서 팔을 뻗으므로 m±w
  두 점이 정확히 일치 → 틈 없이 한 줄로 이어진다.
- 보이는 옆면은 팔의 **긴 변**(진행 방향과 평행)에만 세운다. 허브는 연결되지 않은 방향의
  면만 세운다(끝단 마감). 연결된 쪽 면은 내부면이라 생략.
- 모든 점을 실제 꼭짓점(p_n/p_e/p_s/p_w, corner_elev 반영)에서 파생 → 산비탈에서도 이음매가
  맞고, 4방향 화면 회전에서도 그대로 동작.
- 한 타일 안에서도 블록(허브·팔)을 화면 깊이(y) 순으로 정렬해 뒤→앞으로 그리고, 각 블록은
  옆면을 뒤→앞 순으로 그린 뒤 상판으로 덮는다(`_draw_wall_block`).
- 면 밝기는 "화면 오른쪽을 향한 면 = 밝게, 왼쪽 = 그늘"로 결정 — 회전과 무관하게 일관.
- 대각 연결(`_draw_wall_diag`)도 같은 블록 함수로 통일: 허브 모서리점에서 대각 이웃과 공유하는
  꼭짓점까지 같은 두께의 팔.
- 상수: `WALL_THICK_K = 0.22`(두께), `WALL_HEIGHT = 18.0`.

### 검증
`--headless --import` 파싱 에러 없음만 확인. 사용자 지시에 따라 게임 테스트는 하지 않음 —
사용자가 직접 확인 예정.

## 21순위 구현 완료: 4대문 — 옹성은 성 밖으로, 4방향 대각선 뷰 대응 (P38)

작성 시각: 2026-09-29 (위 "21순위 설계" 그대로 구현)

- `_gate_outward_edge(x,y)`: 성문 양옆 성곽 연결로 성벽 축을 구하고, 그에 수직인 두 방향 중
